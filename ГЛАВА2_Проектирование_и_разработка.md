# Глава 2. Проектирование и разработка приложения

## 2.1. Постановка задач и функциональные требования

### 2.1.1. Анализ предметной области

Мебельная фабрика представляет собой предприятие, занимающееся производством и реализацией мебельной продукции на заказ. В рамках своей деятельности фабрика взаимодействует с двумя основными категориями пользователей: клиентами (заказчиками) и менеджерами (сотрудниками фабрики). Каждая категория имеет свои уникальные потребности и сценарии использования программного обеспечения.

Традиционно учёт заказов на мебельных производствах осуществляется с использованием бумажной документации, электронных таблиц или разрозненных программных решений, что приводит к ряду проблем: задержки в обработке заявок, потеря данных, отсутствие прозрачности статуса заказа для клиента, сложность отслеживания истории взаимодействия с заказчиками. Разработка специализированного мобильного приложения призвана решить перечисленные проблемы путём автоматизации ключевых бизнес-процессов фабрики.

### 2.1.2. Функциональные требования к системе

На основе анализа предметной области были сформулированы функциональные требования, разделённые по категориям пользователей.

**Требования для клиента (заказчика):**
- Регистрация в системе и авторизация с использованием адреса электронной почты и пароля.
- Просмотр списка собственных заказов с отображением текущего статуса каждого заказа и статистикой (всего, активных, новых, завершённых).
- Создание нового заказа с указанием типа изделия, габаритных размеров, комментариев и загрузкой фотографий-референсов (до 5 фото, сохранение в Base64 в Firestore).
- Просмотр детальной информации по конкретному заказу, включая историю изменения статусов, финансовую информацию (бюджет, предоплата, расходы, прибыль), информацию о мастере, фотографии изделия.
- Встроенный чат с менеджером для оперативного обсуждения заказа.
- Возможность оставления отзыва после завершения заказа.
- Просмотр и редактирование профиля пользователя, включая контактные данные и адрес доставки.
- Прямые кнопки звонка и SMS менеджеру. Тёмная и светлая тема.

**Требования для менеджера (сотрудника фабрики):**
- Авторизация в системе с использованием специального кода доступа при регистрации.
- Просмотр списка всех заказов с возможностью фильтрации по статусу (Все, Новые, Мои, В работе, Готовы, Завершены, Оплачен).
- Dashboard — панель управления с ключевыми метриками (новые заказы, в работе, завершённые, общая выручка, прибыль).
- Просмотр списка клиентов с возможностью поиска по имени, телефону или email.
- Просмотр детальной информации о клиенте, включая историю его заказов, контактные данные и статистику.
- Назначение заказа на менеджера и изменение статуса заказа по мере его выполнения.
- Встроенный чат с клиентом для каждого заказа.
- Статистика по заказам (графики и аналитика).
- Просмотр и редактирование собственного профиля.

**Общие требования:**
- Аутентификация и авторизация всех пользователей через Firebase Authentication.
- Хранение данных в Firebase Firestore с синхронизацией в реальном времени.
- Push-уведомления через Firebase Cloud Messaging (FCM).
- Защита персональных данных пользователей.
- Поддержка тёмной и светлой темы оформления с динамическими цветами Android 12+.
- Современный интерфейс на Jetpack Compose с Material Design 3.

### 2.1.4. Нефункциональные требования

Помимо функциональных требований, к системе предъявляются следующие нефункциональные требования:

- **Производительность:** время отклика интерфейса не должно превышать 300 мс при выполнении стандартных операций; данные обновляются в реальном времени через Firestore snapshot listeners.
- **Масштабируемость:** архитектура должна поддерживать возможность добавления новых модулей и функциональности без существенной переработки существующего кода (многомодульная структура).
- **Надёжность:** система должна корректно обрабатывать ошибки сети и отображать понятные пользователю сообщения.
- **Безопасность:** аутентификация должна осуществляться через Firebase Authentication; передача данных — по защищённому протоколу HTTPS.
- **Поддержка устройств:** приложение должно функционировать на устройствах с Android 7.0 (API 24) и выше.

## 2.2. Разработка архитектуры приложения и интерфейса

### 2.2.1. Выбор архитектурного паттерна

Для обеспечения модульности, тестируемости и поддержки кода было принято решение использовать архитектурный паттерн **MVVM (Model-View-ViewModel)** в сочетании с **многомодульной архитектурой** приложения. MVVM является стандартом для современных Android-приложений, использующих Jetpack Compose, поскольку ViewModel работает в связке с Compose через механизм реактивного сбора данных (StateFlow / collectAsState).

Дополнительно применяется паттерн **Repository**, который абстрагирует источники данных (Firebase Firestore, Firebase Storage) и предоставляет ViewModel единый интерфейс для работы с данными через Flow (корутины).

### 2.2.2. Общая архитектура приложения

Приложение KronaERP имеет многомодульную структуру, включающую 7 модулей (рисунок 2.3):

*[Вставить рисунок 2.3 — Диаграмма модулей приложения]*

**Состав модулей:**

1. **`:app`** — главный модуль приложения, точка входа. Содержит класс Application, MainActivity, тему оформления (Material3 с поддержкой Dynamic Colors), ресурсы и SplashScreen.
2. **`:core:network`** — сетевой слой, абстракции над Firebase (Auth, Firestore, Storage), DI-модули Hilt и разделяемые сетевые модели данных (UserProfile, OrderStatus enum).

6. **`:feature:manager`** — модуль менеджерской части: управление заказами с фильтрацией, Dashboard со статистикой, клиенты с поиском, детали клиента, чат, статистика заказов.
7. **`:feature:navigation`** — модуль навигации: AppNavigationViewModel, KronaNavHost, три графа навигации (Auth, Client, Manager).

```
 ├── :feature:manager (зависит от :core:network, :core:uikit)
```

```kotlin
sealed class NavigationState {
    data object Loading : NavigationState()
    data object Auth : NavigationState()
    data object Client : NavigationState()
    data object Manager : NavigationState()
}

@Composable
fun KronaAppNavigation(viewModel: AppNavigationViewModel = hiltViewModel()) {
    val navigationState by viewModel.navigationState.collectAsStateWithLifecycle()
    val startDestination by remember { mutableStateOf(initialStartDestination(navigationState)) }

    LaunchedEffect(navigationState) {
        when (navigationState) {
            is NavigationState.Auth -> navController.navigate(AuthDestinations.AuthDestinationGraph) { popUpTo(0) { inclusive = true } }
            is NavigationState.Client -> navController.navigate(ClientDestinations.ClientGraph) { popUpTo(0) { inclusive = true } }
            is NavigationState.Manager -> navController.navigate(ManagerDestinations.ManagerGraphDestinaion) { popUpTo(0) { inclusive = true } }
            else -> {}
        }
    }

    KronaNavHost(navController = navController, startDestination = startDestination)
}
```

## 2.3. Выбор технологического стека и средств разработки

### 2.3.1. Язык программирования — Kotlin

Kotlin является официальным языком разработки для Android, начиная с Google I/O 2019. Выбор Kotlin обусловлен следующими преимуществами:
- **Полная совместимость с Java** — возможность использования всех существующих Java-библиотек.
- **Null-безопасность** — встроенная система типов, предотвращающая ошибки, связанные с null-значениями.
- **Coroutines** — встроенная поддержка асинхронного программирования через корутины и Flow для реактивных потоков данных.
- **Extension-функции** — возможность расширения существующих классов без наследования.
- **Data-классы** — лаконичный синтаксис для создания моделей данных с автоматической генерацией equals(), hashCode(), toString().

### 2.3.2. Средства разработки пользовательского интерфейса — Jetpack Compose

Jetpack Compose — современный декларативный UI-фреймворк для Android, основанный на composable-функциях. В отличие от традиционного подхода на основе XML-разметки, Jetpack Compose позволяет описывать интерфейс непосредственно в Kotlin-коде, что обеспечивает:

- **Декларативный подход** — описание того, как интерфейс должен выглядеть при заданном состоянии, а не последовательности шагов по его изменению.
- **Реактивность** — автоматическое обновление интерфейса при изменении состояния.
- **Меньше кода** — сокращение объёма кода по сравнению с XML-разметкой в среднем на 30-40%.

### 2.3.3. Внедрение зависимостей — Dagger Hilt

## 2.5. Data Flow и реактивность

Все данные в приложении передаются через реактивные потоки с использованием корутин Kotlin и Flow.

**Схема Data Flow:**
```
Composable (collectAsStateWithLifecycle)
  -> ViewModel (StateFlow, viewModelScope.launch)
    -> Repository (callbackFlow, addSnapshotListener)
      -> Firestore / Firebase Auth / Firebase Storage
```

**Загрузка заказов (пример):**
```kotlin
// 1. Repository — snapshot listener в callbackFlow
fun getAllOrders(): Flow<List<Order>> = callbackFlow {
    val listener = firestore.collection("orders")
        .addSnapshotListener { snapshot, error ->
            if (error != null) { close(error); return@addSnapshotListener }
            trySend(snapshot?.documents?.mapNotNull {
                it.toObject(Order::class.java)?.copy(id = it.id)
            } ?: emptyList())
        }
    awaitClose { listener.remove() }
}

// 2. ViewModel — собирает поток и фильтрует
init {
    viewModelScope.launch {
        repository.getAllOrders().collect { orders ->
            _allOrders.value = orders
            applyFilter()
        }
    }
}

// 3. Composable — подписывается на StateFlow
val orders by viewModel.orders.collectAsState()
```

Этот подход обеспечивает автоматическое обновление интерфейса при изменениях в Firestore без необходимости ручного обновления или polling'а.

## 2.6. Обработка изображений

Фотографии заказов сохраняются непосредственно в Firestore в формате Base64 в поле `imageUrls: List<String>`. Это упрощает архитектуру, устраняя необходимость в отдельном файловом хранилище для каждой фотографии заказа.

**Сохранение:**
```kotlin
// Конвертация URI -> Base64
suspend fun uriToBase64(context: Context, uri: Uri): String {
    val bitmap = MediaStore.Images.Media.getBitmap(context.contentResolver, uri)
    val stream = ByteArrayOutputStream()
    bitmap.compress(Bitmap.CompressFormat.JPEG, 80, stream)
    val bytes = stream.toByteArray()
    return "data:image/jpeg;base64,${Base64.encodeToString(bytes, Base64.DEFAULT)}"
}
```

**Загрузка и отображение:**
```kotlin
@Composable
private fun decodedImage(base64: String?): ImageBitmap? = remember(base64) {
    if (base64 == null) return@remember null
    try {
        val raw = base64.substringAfter("base64,")
        val bytes = Base64.decode(raw, Base64.DEFAULT)
        BitmapFactory.decodeByteArray(bytes, 0, bytes.size)?.asImageBitmap()
    } catch (_: Exception) { null }
}

// Использование:
Image(
    bitmap = decodedImage(url)!!,
    contentDescription = "Фото заказа",
    modifier = Modifier.fillMaxWidth().height(220.dp).clip(RoundedCornerShape(12.dp)),
    contentScale = ContentScale.Crop
)
```

## 2.7. Push-уведомления (FCM)

Для отправки уведомлений используется Firebase Cloud Messaging (FCM).

**Механизм работы:**
1. При входе в систему токен устройства (FCM token) сохраняется в Firestore в поле `fcmToken` пользователя.
2. При изменении статуса заказа или отправке нового сообщения, серверное (или клиентское) приложение отправляет push-уведомление через FCM API.
3. Получатель получает уведомление с заголовком и текстом, при клике открывается соответствующий экран.
